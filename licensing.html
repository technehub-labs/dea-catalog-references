4. Personal-data hygiene + LIA

The IANA registries publish registrant contacts as personal names (typically in the form First_Last). CC0 grants a public-domain dedication for copyright; it does not cover data-protection rights, so the mirror ships a deterministic redaction of any <xref type="person"> data field.

Purpose

Publication of a stable, machine-readable, identifier-anchored index of IANA's public protocol registries so that OpenDEA catalog systems can resolve canonical references (application/json, https) to a single canonical page.

Necessity

Personal-name republication is NOT necessary for the legitimate interest. The contact name carries no operational value to a consumer resolving an identifier; removing it has no impact on the index's dereferencing, lookup, or reference-resolution value.

Balance

The natural-person interest in not being publicly re-indexed outweighs the publisher's interest in presenting the contact name (which is informational, non-load-bearing). With the redaction in place, the residual processing is limited to publishing an opaque structural count per record, which does not constitute the processing of personal data.

4.1 The redaction (technical control)

The parser substitutes every <xref type="person"> data with a deterministic opaque token:

redacted:person:<6-char-prefix-of-sha256-of(name+salt)>

where the salt is the literal string openDEA-catalog-refs-v1. Properties:

  • Deterministic. Same input name → same token. Lets consumers detect cross-record appearances and detect snapshot drift without ever seeing the personal name.
  • Reversible by design. The salt is public. The goal is to remove the mirror's directory function (flip the legal posture), not to defeat forensic adversaries who already have the candidate list from IANA.
  • Structural signal preserved. Every record carries references_count_by_type, so the count and distribution of registrant contacts stays visible to consumers.
  • Verifiable. scripts/validate-data.py::validate_person_xref_redaction() rejects any record whose references[].type = "person" carries a data value other than the redaction token format. The CI gate fails if any code path re-introduces a raw name.

5. Operational notes

  • Authoritative source. The per-record HTML page on this mirror always links to the IANA registry page as the canonical source for the identity behind any redacted token. Registrants seeking to exercise GDPR / UK-GDPR / similar rights over their contact data should contact the original registration authority (typically the IETF or the standards body that registered the value); IANA itself acknowledges that "the rights that other persons may have in the work" are unaffected by CC0.
  • Salt and reversibility. The salt openDEA-catalog-refs-v1 is published. The redaction is a soft (transparent, hashed, structural) redaction; it is not cryptographic irreversibility. The threat model is "stop the mirror from being an indexing vector for contact spam or marketing tooling", which it does.
  • Future changes. Any future change to the redaction token format (e.g. a longer prefix, or a different hash) must update the validator pattern and the documentation here. The validator is the gate.
